01. 병목을 프로세스와 실행 계획으로 좁히기

게이트웨이와 센서 측정 시각 범위로 타임라인을 조회하는 API가 느렸습니다.
Java 앱과 MySQL이 같은 서버에 있어 전체 CPU만으로는 어느 쪽을 먼저 조사해야 할지 판단하기 어려웠습니다.

요청 중 프로세스별 CPU를 확인했을 때 mysqld 사용률이 순간 약 60%까지 상승했습니다.
DB를 우선 조사하고 EXPLAIN FORMAT=JSON으로 조회 계획을 확인했습니다.

센서 수집 테이블은 ALL 접근으로 전체 약 272만 행을 스캔할 것으로 추정됐습니다.
코드와 스키마 파일에 있던 복합 인덱스가 실제 DB에는 없었습니다.
ddl-auto: none 환경이었으며

02. 측정 시각의 의미를 유지한 인덱스

(gateway_collect_id, sensor_timestamp) 복합 인덱스를 적용했습니다.
조인되는 게이트웨이 수집 ID로 후보를 좁힌 뒤 센서 측정 시각을 인덱스 단계에서 검사하도록 했습니다.

게이트웨이 전송 시각에 같은 기간 조건을 추가하지 않았습니다. 늦게 전송된 데이터도 센서의 측정 시각이 조회 범위에 들어오면 보여줘야 하기 때문입니다.

-- 인덱스 구성 예시
CREATE INDEX idx_sensor_gateway_time
ON sensor_reading (gateway_collect_id, sensor_timestamp);

첫 인덱스 생성은 디스크 공간 부족으로 실패했습니다.
공간을 확보한 뒤 다시 적용했습니다.

03. 인덱스 적용 전후 비교

지표적용 전적용 후
접근 방식ALLref
예상 탐색량전체 약 272만 행외부 게이트웨이 수집 행당 약 3행
시간 조건 처리스캔 후 검사index_condition
옵티마이저 추정 비용321,778.145.54
응답 시간 관찰값약 2,130ms약 667ms
mysqld 순간 CPU약 60%약 3%

전체 테이블 스캔이 인덱스 기반 조회로 바뀌었으며, 임시 테이블과 filesort는 남았습니다.
