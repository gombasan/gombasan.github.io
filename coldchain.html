01. CPU 사용량과 실행 계획으로 원인 찾기

특정 게이트웨이의 센서 데이터를 측정 시각 범위로 조회할 때 응답이 느렸습니다.
Java 앱과 MySQL이 같은 서버에 있어 전체 CPU만으로는 어느 쪽을 먼저 조사해야 할지 판단하기 어려웠습니다.

요청 중 프로세스별 CPU를 확인했을 때 mysqld 사용률이 순간 약 60%까지 상승했습니다.
DB를 우선 조사하고 EXPLAIN FORMAT=JSON으로 조회 계획을 확인했습니다.

게이트웨이 키와 센서 측정 시각 범위를 지정해 아래 SQL로 실행 계획을 확인했습니다. GATEWAY_KEY는 예시 값입니다. 

EXPLAIN FORMAT=JSON
SELECT c.*
FROM refrigerant.coldchain_collect AS c
JOIN refrigerant.gateway_collect AS g ON g.id = c.gateway_collect_id
WHERE g.gateway_key = 'GATEWAY_KEY'
  AND c.sensor_timestamp BETWEEN '2026-10-30 00:30:18.810'
                             AND '2026-10-30 02:54:25.793'
ORDER BY c.sensor_timestamp, c.id;

게이트웨이 수집 테이블은 기존 인덱스를 사용했지만, 센서 수집 테이블은 access_type: ALL로 약 272만 행을 탐색할 것으로 추정됐습니다. 약 2시간 24분 범위의 조회에서도 전체 센서 수집 테이블을 스캔하는 계획이었습니다.

운영 DB를 확인하니 코드와 스키마 파일에 정의된 복합 인덱스가 빠져 있었습니다. ddl-auto: none 설정에서는 엔티티의 인덱스 선언이 DB에 자동으로 반영되지 않습니다.

02. 조회 조건을 유지하면서 인덱스 추가

(gateway_collect_id, sensor_timestamp) 복합 인덱스를 적용했습니다.
게이트웨이 수집 ID로 먼저 데이터를 찾고, 인덱스에서 센서 측정 시각 조건을 확인하도록 했습니다.

게이트웨이 전송 시각에 같은 기간 조건을 추가하지 않았습니다. 늦게 전송된 데이터도 센서의 측정 시각이 조회 범위에 들어오면 보여줘야 하기 때문입니다. 

CREATE INDEX idx_coldchain_collect_gateway_timestamp
ON refrigerant.coldchain_collect (gateway_collect_id, sensor_timestamp);

03. 인덱스 적용 전후 비교

지표 적용 전 적용 후
접근 방식 ALL ref
예상 탐색량 전체 약 272만 행 외부 게이트웨이 수집 행당 약 3행
시간 조건 처리 스캔 후 검사 index_condition
옵티마이저 추정 비용 321,778.14 5.54
응답 시간 평균값 약 2,000ms 약 250ms
mysqld 순간 CPU 약 60% 약 3%

전체 테이블 스캔이 인덱스 기반 조회로 바뀌었고, 임시 테이블과 filesort는 남았습니다.
