IoT / ENGINEERING NOTE

가상 게이트웨이로
TCP 수집 서버 검증하기

기존 EC2와 DB로 500대의 동시 접속을 처리할 수 있는지 테스트하고, 1,000대로 늘렸을 때 응답이 늦어지는 원인을 살펴봤습니다.

목표와 수집 구조

냉매와 콜드체인은 조회할 내용은 달랐지만, TCP로 센서 데이터를 수집하는 방식은 같았습니다.
공통 TCP 수집 기능과 device-core의 장비 모델과 설정을 재사용했습니다.
조회와 알림은 서비스별로 개발할 수 있도록 분리했습니다.

TCP 수신완전한 프레임까지 버퍼링 후 파싱
→
저장과 응답Outbox 저장과 커밋 후 ACK 전송
→
이벤트 전달별도 작업에서 HTTP로 전송하고 실패 시 재시도

데이터가 한 번에 모두 전송되지 않는 경우에도 순서대로 이어 보낼 수 있도록 큐를 두고, Selector 스레드에서 전송했습니다.
TCP 입출력과 데이터 처리 작업을 분리한 뒤 배포된 EC2에서 DB 저장과 ACK까지 시험했습니다.

시험 환경과 방법

1차 양산을 위해 검토하던 장비 수는 500대였습니다.
기존 EC2와 DB가 500대를 처리할 수 있는지 확인하고, 장비가 늘어날 경우를 고려해 1,000대까지 테스트했습니다.
PoC에서 쓰는 DB 인스턴스를 함께 사용하고, 테스트용 스키마는 따로 만들었습니다.

시험 결과

동시 접속 시험확인 결과판단
500대 × 5회2,500건 모두 10초 이내 ACK시험 환경에서 목표 규모 확인
1,000대 첫 회차연결 성립, 114건은 10초 내 ACK 미수신커넥션 대기와 쿼리 실행, 커밋 지연이 원인으로 보였음

부하 증가에 따른 병목 확인

로컬에서는 풀 크기를 50으로 늘려 응답이 빨라지는 것을 확인했습니다.
PoC와 DB를 함께 쓰고 있었고 500대 테스트는 통과했기 때문에, 배포 환경의 커넥션 풀 크기는 바꾸지 않았습니다.

테스트 시나리오와 측정 항목은 직접 정했습니다.
생성형 AI를 활용해 Node.js로 가상 게이트웨이 테스트 화면을 만들었습니다.
각 회차의 결과를 그래프로 표시하고 JSON으로 저장했습니다.
